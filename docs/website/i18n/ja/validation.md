# 検証とサポート範囲

checkout の検証方法と、それぞれのチェックから判断できる範囲を説明します。チームの試行記録、業務 patch、課題 ID、マシンやアカウントの状態は公開リポジトリの外に保管します。

## 必須のローカルチェック {#required-local-checks}

package.json に固定された開発バージョンを使用します。

```sh
npm ci
npm --prefix docs/website ci
npm run lint
npm run typecheck
npm test
npm run test:bun
npm run test:e2e
npm run docs:check
npm run site:build
npm run site:check
node scripts/check-package.mjs
```

単体テストは注入したポートを通じてドメインの判断とアプリケーションの流れを検証します。E2e は一時設定とリポジトリ fixture を使ってビルド済み CLI を実行します。CLI 文書のチェックは再ビルドして生成結果を比較します。サイトは正本の Markdown から生成し、ソースの鮮度、内部リンク、資産をチェックします。[サイトガイド](website/README.md)を参照してください。パッケージのスキャンは内蔵 Skill と公開文書を含む配布対象を検査します。

ローカルの成功だけでは実アカウントの権限、リモート資源の存在、パッケージの公開、ホストの有効化は証明できません。非公開の検証記録にリビジョン、ランタイム、正確なコマンドを残し、資格情報、実応答、会話記録はコミットしないでください。

## 実環境との連携 {#live-integrations}

`npm run test:contract` は任意の読み取り専用チェックです。[README の開発節](../README.md#development)にある明示的な座標を使います。入力不足ならスキップし、設定済みなのにアクセスできなければ失敗します。

認証は連携ツールが管理します。対応するローカル資格情報を使い、fixture にコピーしません。ホストのプロジェクト信頼は別の境界です。構文的に正しい hook/MCP ファイルは、有効化の証明にはなりません。実際の source push や PR には、インストール済み連携ツールによるフォーク親子関係の根拠も必要です。

## プラットフォームの検証範囲 {#platform-coverage}

POSIX の自動チェックはプロセス管理、ファイル所有権、CLI 動作を検証します。Windows アダプターは実装済みですが、実行、ボリューム間 junction、ホスト有効化には独立した [Windows 検証](design/windows.md)が必要です。POSIX 実行やプラットフォームフラグの注入から Windows の結果を推測しません。

Agent のプロトコルは異なります。`hook list`、`mcp list/show` で対応、非対応、未検証を区別し、公開時の説明にも残してください。

## 独立した Agent 評価 {#independent-agent-evaluation}

[評価プロトコル](eval/README.md)はワークスペースの発見、準備状態、Skill 選択、ソースの追跡、タスク品質を扱います。fixture または明示的に承認された非公開マニフェストで実施します。完全な証拠は公開リポジトリの外に保管し、レビューした集計結果だけを公開します。

## 公開ソースのスナップショット {#preparing-a-public-source-snapshot}

npm の配布物スキャンは Git リポジトリ全体のレビューではありません。ソース、テスト、例、文書、patch、無視対象、履歴を別々に確認します。架空の例でもプロトコルの意味を保ち、組織の実際の構成や識別子は使いません。

作業ツリーのファイル削除では過去のコミットは消えません。公開スナップショットは `.git` を含めず新しい履歴を始められますが、非公開の原本を保管してください。履歴の書き換えや公開は別の操作です。本プロジェクトは Apache-2.0 を採用しています。公開時には引き続き第三者表記と配布物のライセンス本文を確認します。public npm での配布はチームのマニフェストを公開せず、連携パッケージの配布方針も変更しません。fx 自体の移行は[公開チェックリスト](public-release.md)を参照してください。
